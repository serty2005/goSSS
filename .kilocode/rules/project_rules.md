# Правила работы над проектом Etalon-Server

## Общее описание и назначение системы

"Etalon-Server" — это центральный сервер-агрегатор, предназначенный для создания "эталонной" базы данных об IT-инфраструктуре клиентов. Он решает следующие задачи:

Агрегация данных: Собирает информацию о сущностях (Company, Server, Workstation, FiscalRegister) из различных источников (ServiceDesk, FTP, API агентов, опрос серверов).

Сверка и обогащение: Сравнивает данные из разных источников, находит расхождения, обогащает локальную базу данных.

Создание задач: При обнаружении конфликтов (например, data_conflict, owner_mismatch, need_update) автоматически создает задачи для ручного разбора оператором - они должны быть видны во фронтовом интерфейсе на Vue

Предоставление API: Отдает данные через REST API для фронтенд-приложения (Vue.js), которое используется операторами для поиска, просмотра информации и решения задач.

Изменение внешней системы: Предоставляет инструменты для операторов, чтобы по их команде асинхронно вносить изменения в ServiceDesk (создавать и обновлять сущности), приводя внешний источник правды в соответствие с реальностью.

## Структура проекта

Проект написан на Go и следует принципам Clean Architecture.

- `cmd/`: Точки входа приложений (etalon-server, test_logger).

- `internal/`: Внутренний код.

  - `app/`: Инициализация приложения.

  - `contextkeys/`: Ключи для контекста.

  - `core/`: Ядро системы.

    - `events/`: События.

    - `gateways/`: Шлюзы для внешних источников (agent_ftp, duplicates, sdesk, server_polling).

    - `processing/`: Обработка (orchestrator, engine).

    - `workers/`: Фоновые воркеры (fr_update_founder, sd_editor_worker, status_actuality_worker).

  - `domain/`: Бизнес-логика.

    - `constant.go`: Константы.

    - `models/`: Модели данных.

    - `repositories/`: Репозитории для доступа к данным.

  - `infra/`: Инфраструктура.

    - `config/`: Конфигурация.

    - `db/`: База данных и миграции.

    - `external/`: Внешние клиенты.

    - `iiko/`: Интеграция с iiko.

    - `logger/`: Логирование.

    - `plugins/`: Плагины (naumen).

  - `services/`: Бизнес-сервисы.

  - `transport/http/`: HTTP транспорт.

    - `dtos/`: DTO для API.

    - `handlers/`: Обработчики запросов.

    - `middleware/`: Промежуточное ПО.

    - `validators/`: Валидаторы.

- `tools/`: Инструменты (seeder с mock данными).

- Корневые файлы: Dockerfile, go.mod, .env.example и т.д.

## Общие правила работы

# Общие правила работы

## Язык
* **Только русский язык:** Все твои ответы, комментарии в коде, логи и сообщения должны быть строго на русском языке.

## Обработка информации
* **Никаких домыслов:** Ты не должен придумывать детали реализации, касающиеся внешних систем или неоднозначных требований. Если информации недостаточно, твоя обязанность — задать мне уточняющие вопросы. Только после получения ответа ты можешь приступать к написанию кода.

## Процесс работы
* **Пошаговая работа:** Мы будем двигаться от задача к задаче. Не генерируй код для всех задач сразу. Начни с первой, задай вопросы, получи ответы и только потом реализуй ее.
* **Планирование объема ответа:** Сразу проверяй, что не помещается в контекстное окно ответа. Останавливай полностью законченные участки кода без заглушек и повторений, когда речь идет о коде модулей целиком. Если изменений требует отдельная функция или структура, приведи её только полностью без пропусков.

## Формат ответа
* **Формат ответа:** Присылай только конкретные правки для файлов, четко указывая, что и где нужно изменить. Не нужно переписывать файлы целиком без необходимости.
* **Актуальные комментарии кода:** Всегда пиши только актуальное объяснение шагов. Без меток ОБНОВЛЕНО или ДОБАВЛЕНО. Отмечай блоки целиком, комментарии в самом коде только по актуальному функционалу.

## Правила дальнейшего развития архитектуры проекта

- Соблюдать разделение на слои: domain не зависит от infra, transport зависит от domain через services.
- Использовать воркеры для асинхронных задач агрегации, сверки и изменений внешних систем.
- Обеспечивать консистентность данных через механизмы сверки и создания задач при конфликтах.
- Развивать REST API постепенно, добавляя новые эндпоинты для фронтенда.
- Тестировать интеграции с внешними источниками (ServiceDesk, FTP, API агентов).
- Поддерживать возможность асинхронного внесения изменений в ServiceDesk по команде операторов.
- Обновлять этот файл при изменениях в проекте для актуальности в следующих сессиях.
