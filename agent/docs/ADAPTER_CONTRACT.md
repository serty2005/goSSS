# Adapter Contract

## Назначение контракта

Этот документ фиксирует базовый контракт взаимодействия между `core-agent` и внешними адаптерами.
Контракт рассчитан на независимую сборку, доставку и обновление адаптеров.
`core-agent` не знает предметную логику адаптера и работает только через стандартные команды и JSON.

## Идентичность адаптера

Каждый адаптер обязан иметь следующую идентичность:

- `adapter_id`: стабильный уникальный идентификатор, например `fiscal-atol`;
- `adapter_type`: тип адаптера, например `fiscal-atol`, `fiscal-shtrih`, `saga-runner`;
- `version`: версия конкретного бинарника адаптера;
- `target_os`: целевая ОС;
- `target_arch`: целевая архитектура;
- `protocol_version`: версия контракта между `core-agent` и адаптером.

## Формат запуска

`core-agent` запускает адаптер как отдельный процесс.
На текущем этапе runtime запуска уже реализован: агент резолвит локальный бинарник через `descriptors/*.json` и каталог `bin/`, стартует процесс адаптера, ожидает JSON-ответ и отправляет структурированный результат обратно на сервер через следующий heartbeat.

### Базовая схема

```text
adapter-binary <command> [flags]
```

### Обязательные команды

- `describe`
- `health`
- `run`

### Общие правила

- вход и выход команды должны быть JSON;
- stdout используется только для полезного JSON-ответа;
- stderr используется для диагностических сообщений;
- адаптер не должен требовать интерактивного ввода;
- адаптер не должен изменять бинарники `core-agent`.

## Runtime Lifecycle

Полный runtime flow для активного агента выглядит так:

1. heartbeat-ответ сервера может одновременно содержать и `adapter_manifests`, и задачи `run_adapter` / `adapter_run`;
2. агент всегда сначала синхронизирует `adapter_manifests` локально и только после этого исполняет задачи;
3. задача запуска содержит `adapter_id`, `command`, `operation`, `timeout` и `device_params`;
4. агент находит актуальный descriptor адаптера в `descriptors/` и локальный бинарник в `bin/`;
5. агент проверяет совместимость `target_os/target_arch`;
6. на Windows агент `amd64` имеет право запускать адаптер `386`, чтобы работать с 32-битными драйверами оборудования;
7. если локальный descriptor или бинарник отсутствует, агент возвращает явную ошибку preflight и не считает такой запуск реально стартовавшим;
8. `last_run_at` обновляется только для фактически стартовавшего процесса адаптера, поэтому preflight-fail не сдвигает расписание;
9. агент запускает бинарник как отдельный процесс, передает JSON в stdin и собирает `stdout`, `stderr`, `exit_code`, `duration`;
10. если процесс завис, агент завершает его по timeout/context;
11. после выполнения агент складывает `task_result` в очередь и отправляет его серверу следующим heartbeat.

## Task Payload От Сервера К Агенту

Операторский UI сохраняет минимальный runtime profile и не показывает низкоуровневые поля подключения. На стороне сервера используется следующий минимальный ввод:

```json
{
  "adapter_id": "fiscal-atol",
  "command": "run",
  "operation": "collect",
  "timeout_seconds": 45,
  "devices": [
    {
      "connection_type": "tcp",
      "address": "10.25.1.22:5555"
    }
  ],
  "schedule": {
    "enabled": true,
    "interval_seconds": 300
  }
}
```

Правила нормализации адреса на сервере:

- `tcp`: `ip[:port]`
- `com`: `COMx`

После нормализации сервер отправляет агенту payload команды запуска такого вида:

```json
{
  "adapter_id": "fiscal-atol",
  "command": "run",
  "operation": "collect",
  "timeout": "45s",
  "protocol_version": "1",
  "request_id": "run-123",
  "device_params": {
    "devices": [
      {
        "connection_type": "tcp",
        "transport": "tcp",
        "ip": "10.25.1.22",
        "port": 5555
      }
    ]
  }
}
```

### Обязательные поля task payload

- `adapter_id`
- `command`
- `timeout` или `timeout_seconds`

### Поля предметного payload для fiscal-* адаптеров

- `device_params.devices[].connection_type`
- `device_params.devices[].transport`
- `device_params.devices[].ip`
- `device_params.devices[].port`
- `device_params.devices[].com_port`
- при необходимости сервер может дополнительно передать `label`, `baudrate`, `model`, `driver_hints`, `extra_params`

## Команда describe

Команда возвращает статическое описание адаптера и его возможностей.

### Вход

```json
{
  "protocol_version": "1",
  "request_id": "uuid"
}
```

### Выход

```json
{
  "adapter_id": "fiscal-atol",
  "adapter_type": "fiscal-atol",
  "version": "1.0.0",
  "target_os": "windows",
  "target_arch": "amd64",
  "protocol_version": "1",
  "capabilities": [
    "inventory",
    "run-task"
  ]
}
```

## Команда health

Команда возвращает текущее состояние готовности адаптера к работе.

### Вход

```json
{
  "protocol_version": "1",
  "request_id": "uuid",
  "timeout_seconds": 10
}
```

### Выход

```json
{
  "status": "ok",
  "message": "adapter is ready",
  "details": {
    "driver_present": true
  }
}
```

### Допустимые статусы

- `ok`
- `degraded`
- `error`

## Команда run

Команда исполняет полезную нагрузку адаптера.

### Вход

```json
{
  "protocol_version": "1",
  "request_id": "uuid",
  "task_type": "example-task",
  "payload": {}
}
```

### Выход

```json
{
  "status": "success",
  "result": {},
  "warnings": []
}
```

### Допустимые статусы run

- `success`
- `partial`
- `failed`

## Формат JSON, Который Агент Передает Адаптеру

Для `command = run` агент передает в stdin JSON следующего вида:

```json
{
  "protocol_version": "1",
  "request_id": "run-123",
  "task_type": "collect",
  "timeout_seconds": 45,
  "payload": {
    "devices": [
      {
        "connection_type": "tcp",
        "transport": "tcp",
        "ip": "10.25.1.22",
        "port": 5555
      }
    ]
  }
}
```

Для `describe` и `health` агент использует тот же envelope, но без `task_type/payload`, если они не нужны конкретной команде.

## Формат Task Result, Который Агент Возвращает Серверу

После выполнения команды агент отправляет в heartbeat:

```json
{
  "id": 42,
  "type": "run_adapter",
  "status": "completed",
  "adapter_id": "fiscal-atol",
  "command": "run",
  "operation": "collect",
  "completed_at": "2026-03-22T10:00:05Z",
  "duration_ms": 3200,
  "exit_code": 0,
  "stdout": "{\"status\":\"success\"}",
  "stderr": "driver hint",
  "result": {
    "status": "success",
    "devices": []
  }
}
```

### Статусы выполнения в task result

- `completed`
- `failed`
- `timeout`
- `canceled`

## Поля Runtime-Статуса В Adapter Statuses

Heartbeat агента публикует по каждому локальному адаптеру:

- `status` — статус локальной поставки бинарника (`ready`, `missing_binary`, `error`);
- `run_status` — статус последнего запуска (`running`, `completed`, `failed`, `timeout`, `canceled`);
- `last_run_at`
- `last_exit_code`
- `last_error`

## Контракт для fiscal-* адаптеров

`fiscal-*` адаптер отвечает только за конкретную предметную интеграцию с устройством и драйвером.

### Обязанности fiscal-* адаптера

- локально обнаруживать поддерживаемые устройства своего семейства;
- проверять наличие требуемых драйверов;
- выполнять узкие команды своего домена;
- возвращать результат только в рамках JSON-контракта.

### Не входит в обязанности fiscal-* адаптера

- хранение серверных токенов;
- регистрация агента;
- скачивание других адаптеров;
- self-update `core-agent`;
- принятие решений о запуске других адаптеров.

## Контракт для saga-runner

`saga-runner` является отдельным адаптером, который исполняет оркеструемые локальные сценарии на клиентской машине.

### Обязанности saga-runner

- получать JSON-задачу от `core-agent`;
- исполнять локальные шаги по фиксированному контракту;
- возвращать структурированный результат выполнения;
- не выходить за пределы разрешённого контекста запуска.

### Ограничения saga-runner

- не управляет регистрацией и heartbeat;
- не заменяет `core-agent`;
- не должен самостоятельно скачивать и устанавливать другие адаптеры без явного протокольного разрешения.

## Базовый JSON-контракт

### Общие поля входа

- `protocol_version`
- `request_id`
- `task_type`
- `payload`
- `timeout_seconds`

Не все поля обязательны для каждой команды, но адаптер должен игнорировать неизвестные поля и корректно обрабатывать отсутствие неиспользуемых полей.

### Общие поля выхода

- `status`
- `message`
- `result`
- `details`
- `warnings`
- `error_code`

## Коды завершения процесса

- `0`: команда успешно выполнена, ответ в stdout валиден;
- `1`: прикладная ошибка выполнения команды;
- `2`: невалидный входной JSON или неизвестная команда;
- `3`: ошибка окружения или отсутствующая локальная зависимость;
- `4`: ошибка совместимости протокола;
- `10+`: зарезервировано под доменные коды адаптера.

`core-agent` должен различать ошибку процесса и ошибку содержимого ответа.

## Ограничения безопасности

- адаптер не должен хранить access/refresh токены `core-agent`;
- адаптер не должен читать или модифицировать защищённое хранилище identity агента;
- адаптер не должен заменять бинарник `core-agent`;
- адаптер не должен запускать интерактивные UI-процессы без отдельного разрешения протокола;
- адаптер не должен исполнять произвольные shell-команды вне своей предметной логики;
- адаптер должен работать только в рамках входного JSON и локальных разрешённых ресурсов.

## Ответственность core-agent

`core-agent` обязан:

- хранить и синхронизировать бинарники адаптеров;
- проверять совместимость адаптера до запуска;
- передавать адаптеру только валидный JSON;
- ограничивать время ожидания и учитывать код завершения процесса;
- логировать факт запуска и результат команды;
- публиковать серверу статус локально установленного адаптера;
- не внедрять предметную логику адаптера внутрь себя.

## Debug Mode

Расширенное debug-логирование включается только через `agent-config.json`:

```json
{
  "debug": true
}
```

В debug-режиме агент дополнительно пишет:

- summary heartbeat request/response;
- полный список полученных `adapter_manifests`;
- решения sync: что уже актуально, что скачивается, куда скачивается и почему пропускается;
- все полученные `run_adapter` задачи и их исходный payload;
- нормализованный stdin payload, который передается адаптеру;
- локальные пути к descriptor и binary;
- попытку старта процесса, `stdout`, `stderr`, `exit_code`, structured result/error;
- обновление `adapter_status` после запуска.

В обычном режиме эти подробные записи в лог не попадают.

## Версионирование контракта

- `protocol_version` обязателен для manifest, `describe`, `health` и `run`;
- несовместимая новая мажорная версия протокола требует отдельной поддержки в `core-agent`;
- добавление новых опциональных полей не должно ломать старые адаптеры и старые версии `core-agent`.
