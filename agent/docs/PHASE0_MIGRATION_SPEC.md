# Phase 0 Migration Spec

## Цель этапа

`Phase 0` фиксирует переход от монолитного `POSRelayd` к архитектуре `core-agent + external adapters`.
Результат этапа: новый Go-агент становится минимальным и устойчивым системным агентом, который умеет идентифицировать машину, поддерживать связь с сервером, собирать inventory, получать manifest адаптеров и синхронизировать локальные бинарники адаптеров без встраивания предметной логики конкретных ФР.

## Целевая архитектура

### Core-agent

`core-agent` отвечает только за общесистемные функции:

- регистрация агента на сервере;
- получение, обновление и хранение токенов;
- heartbeat и выполнение общих серверных задач;
- self-update самого core-agent;
- сбор inventory машины;
- передача серверу inventory и статусов локальных адаптеров;
- приём server-side manifest;
- скачивание, верификация, хранение и обновление адаптеров;
- в дальнейшем запуск адаптеров по фиксированному контракту.

### External adapters

Адаптеры являются отдельными исполняемыми файлами, которые поставляются и обновляются независимо от `core-agent`.
Каждый адаптер реализует узкую предметную область:

- `fiscal-atol`;
- `fiscal-mitsu`;
- `fiscal-shtrih`;
- `saga-runner`;
- другие специализированные агенты в будущем.

Адаптер не управляет регистрацией, токенами, heartbeat или self-update `core-agent`.

## Границы ответственности core-agent

### Входит в ответственность core-agent

- безопасное хранение identity и токенов;
- поддержка мягкой совместимости протокола;
- учёт локального состояния машины;
- хранение каталога адаптеров в `DataDir`;
- контроль совместимости адаптера по `target_os` и `target_arch`;
- контроль целостности бинарника через `sha256`;
- публикация серверу факта наличия и статуса локальных адаптеров.

### Не входит в ответственность core-agent

- прямое управление драйверами Atol, Mitsu, Shtrih;
- поиск и опрос конкретных ККТ;
- бизнес-логика saga-задач;
- удалённый shell;
- собственная логика предметных интеграций с POS/ФР;
- знание внутренних деталей каждого адаптера beyond контракт запуска.

## Объём текущего этапа

### Что входит в Phase 0

- документирование новой архитектуры;
- базовый inventory-first слой;
- базовый adapter manager;
- расширение heartbeat новыми опциональными полями;
- поддержка optional `adapter_manifests` в ответах сервера;
- синхронизация адаптеров без их запуска.

### Что не входит в Phase 0

- перенос логики `POSRelayd` внутрь `core-agent`;
- реализация адаптеров Atol, Mitsu, Shtrih;
- subprocess executor для адаптеров;
- orchestration и retry-политика запуска адаптеров;
- удаление локальных адаптеров по policy сервера;
- полноценный `saga-runner`.

## Модель inventory

Inventory является сериализуемым снимком машины, пригодным для передачи в heartbeat.

### Состав снимка

- `collected_at`: время формирования снимка;
- `hostname`;
- `os`;
- `arch`;
- `executable_path`;
- `network_interfaces[]`;
- `com_ports[]`;
- `installed_software[]`;
- `known_components[]`.

### Network interfaces

Для каждого интерфейса сохраняются:

- системное имя;
- индекс;
- MTU;
- MAC-адрес;
- список IP-адресов;
- набор флагов.

### COM-порты

Для каждого порта сохраняются:

- имя порта, например `COM4`;
- исходное системное устройство;
- источник обнаружения.

### Installed software

Для установленного ПО сохраняются:

- `name`;
- `version`;
- `publisher`;
- `install_location`;
- `uninstall_string`;
- `source`.

### Known components

`known_components` фиксируют признаки присутствия важных для эксплуатации компонентов:

- `atol-drivers-10`;
- `teamviewer`;
- `anydesk`;
- `rustdesk`;
- `litemanager`;
- `iiko-front`;
- `iiko-cashserver`;
- `syrve-front`;
- `syrve-cashserver`.

Для каждого компонента сохраняются:

- логический ключ;
- человекочитаемое имя;
- категория;
- флаг `detected`;
- версия, если она известна;
- список `evidence[]` с указанием типа и источника признака.

## Server-side adapter manifest

Сервер может вернуть в heartbeat список `adapter_manifests`.
Каждый manifest-элемент описывает желаемый локальный бинарник адаптера.

### Обязательные поля manifest

- `adapter_id`;
- `version`;
- `download_url`.

### Базовые опциональные поля manifest

- `adapter_type`;
- `target_os`;
- `target_arch`;
- `protocol_version`;
- `sha256`;
- `file_name`.

### Принципы обработки

- неизвестные поля игнорируются;
- отсутствие `adapter_manifests` не является ошибкой;
- несовместимые по ОС или архитектуре элементы пропускаются;
- совпадающий по версии и `sha256` локальный адаптер не скачивается повторно.

## Жизненный цикл адаптера

На `Phase 0` жизненный цикл ограничен подготовкой бинарника к дальнейшему запуску.

### Стадии

1. Сервер публикует manifest.
2. `core-agent` получает manifest в heartbeat.
3. `core-agent` проверяет совместимость и корректность manifest.
4. `core-agent` скачивает бинарник.
5. `core-agent` проверяет `sha256`, если он задан.
6. `core-agent` атомарно сохраняет бинарник и descriptor локального адаптера.
7. `core-agent` начинает отправлять статус локального адаптера в heartbeat.

### Что пока не делается

- запуск адаптера;
- остановка адаптера;
- health-check subprocess;
- удаление адаптера по отсутствию в manifest.

## Последовательность реализации

### Шаг 1. Документы и контракт

- зафиксировать архитектурные границы `core-agent`;
- зафиксировать контракт адаптера;
- зафиксировать структуру manifest и inventory.

### Шаг 2. Inventory-first core

- добавить сбор системного inventory;
- хранить последний снимок в памяти;
- обновлять снимок по расписанию;
- сделать inventory сериализуемым и пригодным для heartbeat.

### Шаг 3. Adapter manager

- подготовить локальный каталог адаптеров;
- хранить descriptor локально установленных адаптеров;
- добавить совместимость по ОС и архитектуре;
- добавить скачивание и контроль целостности.

### Шаг 4. Runtime integration

- встроить inventory service в runtime;
- встроить adapter manager в runtime;
- отправлять inventory и статусы адаптеров в heartbeat;
- после heartbeat синхронизировать адаптеры из server manifest.

### Шаг 5. Следующий этап после Phase 0

- subprocess executor для адаптеров;
- стандартный lifecycle `describe -> health -> run`;
- выделенный `saga-runner` как отдельный адаптер;
- отдельные адаптеры для Atol, Mitsu и Shtrih по фиксированному контракту.
