# Ревизия текущего этапа и операторский флоу

## Назначение

Документ фиксирует фактическое состояние `goSSSagent` перед переходом к отдельному `saga-runner`.
Цель:

- сверить код с планом миграции `POSRelayd`;
- честно определить готовность к первому боевому тесту;
- зафиксировать единый операторский сценарий работы с агентом;
- определить, что нужно доделать до автоматического назначения адаптеров.

## Покрытие плана миграции

### Phase 0. Core-agent и внешние адаптеры

Статус: в основном закрыта.

Что уже есть:

- bootstrap-регистрация, выдача и refresh токенов;
- heartbeat с `inventory` и `adapter_statuses`;
- adapter manager со скачиванием, проверкой `sha256` и локальными descriptor;
- UI для списка агентов, диагностики heartbeat и подтверждения bootstrap-регистрации;
- отдельные бинарники `fiscal-atol`, `fiscal-mitsu`, `fiscal-shtrih` с командами `describe`, `health`, `run`.

Что еще не закрыто:

- `core-agent` пока не запускает адаптеры как subprocess;
- нет UI/мастера для назначения `adapter_manifests`;
- нет server-side каталога адаптеров и шаблонов профиля машины;
- нет автоматического снятия/замены адаптеров по правилам устройства.

### Phase 1. Конфиг и управление состоянием

Статус: частично закрыта.

Что уже есть:

- конфиг `core-agent`;
- локальное хранение identity и токенов;
- persisted state для connectivity;
- локальный каталог адаптеров с descriptor.

Что еще не закрыто:

- нет отдельного SQLite-хранилища под snapshots/outbox/fiscal_links;
- нет server-side редактора конфигурации агента;
- нет доменной модели профиля машины и шаблонов адаптеров.

### Phase 2. HostInfo и кассовое ПО

Статус: хороший вертикальный срез.

Что уже есть:

- поиск `AppData`;
- чтение `serverUrl` из `iiko/syrve cashserver`;
- `TeamViewerID`, `LiteManagerID`;
- `RustDeskID` через `rustdesk.exe`;
- `AnyDeskID` через `anydesk.exe`.

Что еще не закрыто:

- нет отдельного POS-адаптера для iiko/syrve;
- нет сбора логов, конфигов и диагностики кассового ПО как отдельного домена.

### Fiscal adapters

Статус: готовы к предметным полевым smoke-тестам как отдельные бинарники.

Что уже есть:

- `fiscal-atol`: `health/run`, работа через `fptr10.dll`, выбор ветки драйвера;
- `fiscal-mitsu`: `health/run`, COM/TCP, Mitsu-протокол;
- `fiscal-shtrih`: `health/run`, COM-драйвер `AddIn.DrvFR`.

Что еще не закрыто:

- автодетект оборудования;
- автоматический запуск из `core-agent`;
- унифицированный server-side профиль endpoint-ов;
- fallback/обогащение host metadata внутри предметных адаптеров.

### Saga/task execution

Статус: не готово как отдельная подсистема.

Что уже есть:

- базовый `saga.Runner`;
- один рабочий workflow `self_update`.

Что еще не закрыто:

- нет отдельного `saga-runner` адаптера;
- нет безопасного task-контракта для локальных действий;
- нет operator flow для согласования и запуска task-адаптеров.

## COM-порты и словарь сигнатур

### Что сделано сейчас

`inventory.com_ports` расширен.
Теперь агент отдает не только имя `COM`-порта, но и:

- `enumerator`, `instance_id`;
- `friendly_name`, `description`, `manufacturer`, `class`, `service`, `location`;
- `hardware_ids[]`, `compatible_ids[]`;
- `vendor_id`, `product_id`;
- нормализованную сигнатуру `signature_key`;
- `classification`, если сигнатура уже есть в словаре.

Источники:

- `HKLM\HARDWARE\DEVICEMAP\SERIALCOMM`;
- `HKLM\SYSTEM\CurrentControlSet\Enum`.

### Что это дает оператору

- можно собирать реальные `VEN/DEV` и `VID/PID` с клиентских машин без ручного лазания по реестру;
- можно различать “настоящий физический COM” и абстрактный `COM4` без контекста;
- можно накапливать подтвержденный словарь сигнатур по типам:
  - фискальный регистратор;
  - сканер штрих-кодов;
  - банковский терминал;
  - весы.

### Что еще не сделано

- словарь сигнатур пока пустой по умолчанию;
- нет UI для подтверждения типа устройства и записи правила на сервере;
- нет автоматической выдачи адаптера по `signature_key`.

### Правильная следующая модель

1. Агент присылает `signature_key` и device metadata.
2. Оператор в UI подтверждает тип устройства по конкретной сигнатуре.
3. Сервер сохраняет правило `signature_key -> device_type -> adapter profile`.
4. Следующая машина с тем же устройством автоматически получает нужный адаптер.
5. При исчезновении сигнатуры сервер может убирать лишний адаптер из профиля машины.

## Можно ли вынести iiko/syrve в отдельный адаптер

Вывод: да, это правильное направление.

Причины:

- `core-agent` уже отделен от предметной логики и умеет жить в модели `inventory + manifests + adapter_statuses`;
- `hostinfo` уже умеет находить `cashserver` и определять `serverUrl`;
- `inventory.known_components` уже показывает признаки `iiko-front`, `iiko-cashserver`, `syrve-front`, `syrve-cashserver`;
- сервер уже использует `url_rms` и remote ID для сопоставления машины с оборудованием;
- кассовое ПО имеет свою предметную зону: конфиги, логи, сервисные файлы, версии, диагностические артефакты.

### Рекомендуемая ответственность POS-адаптера

Отдельный адаптер iiko/syrve должен отвечать только за:

- сбор конфигов cashserver/front;
- чтение и нормализацию путей;
- сбор диагностических логов;
- чтение специфичных версий бинарников;
- возврат POS-специфичного JSON по стандартному контракту адаптера.

Он не должен:

- хранить токены `core-agent`;
- управлять heartbeat;
- решать, какие еще адаптеры запускать;
- дублировать общий inventory.

### Когда его подключать

Триггеры для подключения:

- найден `cash_server_url`;
- обнаружен `iiko-cashserver` или `syrve-cashserver`;
- обнаружен `iiko-front` или `syrve-front`;
- серверный профиль машины явно помечен как POS-станция.

### Что мешает прямо сейчас

- нет server-side шаблона профиля машины;
- нет UI, где оператор назначает POS-адаптер;
- нет отдельного контракта результата для POS-специфичных данных.

## Готовность к первому боевому тесту

### Что уже можно тестировать вживую

- bootstrap-регистрацию и approval;
- первый heartbeat;
- inventory;
- hostinfo и remote ID;
- enriched COM inventory;
- синхронизацию бинарников адаптеров через manifest;
- диагностику в UI;
- прямые smoke-тесты самих `fiscal-*` адаптеров как отдельных бинарников.

### Что еще нельзя считать production-ready

- автоматическое назначение адаптеров по типу машины;
- автодетект оборудования внутри `core-agent`;
- task execution через отдельный `saga-runner`;
- полностью замкнутый UI-сценарий “обнаружил машину -> назначил набор адаптеров -> получил предметные данные”.

### Итоговый вердикт

К первому боевому тесту готов именно `core-agent inventory-first` контур.

Не готово к полноценному production-пилоту в автоматическом режиме:

- управление профилем адаптеров из UI;
- автоматическое распознавание типа COM-устройства по накопленному словарю;
- отдельный task-адаптер по паттерну саги.

## Единый операторский флоу

### Целевой практический сценарий на текущем этапе

1. Оператор открывает раздел `Агенты` и видит новый `sssruner`.
2. Если статус регистрации `pending_approval`, оператор подтверждает bootstrap в карточке диагностики.
3. После первого heartbeat оператор открывает `Inventory snapshot`.
4. В `Host info` проверяет:
   - `cash_server_product`;
   - `cash_server_url`;
   - remote IDs.
5. В `COM-портах` смотрит:
   - `friendly_name`;
   - `signature_key`;
   - `hardware_ids`;
   - наличие или отсутствие `classification`.
6. По `known_components` и `host_info` определяет класс машины:
   - обычная рабочая станция;
   - касса с iiko/syrve;
   - машина с фискальным оборудованием;
   - гибридная машина.
7. Назначает набор `adapter_manifests` вручную через серверную конфигурацию.
8. Проверяет появление `adapter_statuses`.
9. Переходит в `Наблюдения агента` и смотрит фактические payload-ы.
10. Только после стабилизации этой цепочки переходим к отдельному `saga-runner`.

### Как должен выглядеть следующий улучшенный флоу

1. Агент регистрируется.
2. Оператор подтверждает регистрацию.
3. Агент присылает inventory.
4. UI показывает рекомендованный профиль машины.
5. Оператор подтверждает или корректирует профиль.
6. Сервер сам формирует `adapter_manifests`.
7. Агент синхронизирует и запускает адаптеры.
8. UI показывает статусы, ошибки и предметные payload-ы.

## Минимальный backlog перед `saga-runner`

Приоритет `P0`:

- server-side редактор профиля агента и `adapter_manifests`;
- накопление реального словаря `signature_key -> device_type`;
- subprocess lifecycle для адаптеров в `core-agent`;
- шаблоны профилей машины по inventory/known components.

Приоритет `P1`:

- отдельный POS-адаптер для iiko/syrve;
- автоматические рекомендации по набору адаптеров;
- health/run orchestration для предметных адаптеров.

Приоритет `P2`:

- отдельный `saga-runner` адаптер;
- task-контракт и операторское согласование локальных действий.
