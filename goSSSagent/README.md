# goSSSagent (текущий этап)

Агент находится на раннем этапе разработки и сейчас решает только две задачи:

1. Регистрация на сервере ServiceDesk.
2. Периодический `heartbeat` для отображения онлайн-статуса рабочей станции.
3. Самообновление по задаче от сервера (`self_update`), полученной в ответ на `heartbeat`.

## Важно

- Файл `goSSSagent/1prompt` не удаляется.
- В нём содержатся важные инструкции по извлечению `CRMid` из логов `iikoFront` для следующих этапов разработки.

## Разделение типов агентов

На бэкенде должны существовать разные типы агентов с разным поведением:

- `getad` (или другой простой сборщик данных):
  - отправляет данные через `/api/submit_json` или `/api/agents/.../data`;
  - не получает задачи на выполнение;
  - используется как репортер данных.

- `sssruner` (новый агент, этот проект):
  - регистрируется на сервере;
  - шлёт `heartbeat`;
  - получает задачи в ответ на `heartbeat`;
  - выполняет задачи по жёстким сценариям (в дальнейшем через паттерн саг).

По умолчанию `goSSSagent` отправляет тип агента `sssruner`.

## Что уже реализовано

- Хранение постоянного `UUID` агента в файле `agent.uuid`.
- Регистрация агента через `POST /api/agents/register`.
- Отправка heartbeat через `POST /api/agents/{uuid}/data`.
- Повторная регистрация, если heartbeat вернул `404`.
- Получение задач от сервера (только для типа `sssruner`).
- Каркас выполнения задач через простой `saga runner`.
- Первый workflow: `self_update`.

## Что пока НЕ реализовано

- Извлечение `CRMid` и других данных из логов `iikoFront`.
- Отправка результатов выполнения задач обратно на сервер.
- Очередь/ретраи задач с сохранением состояния.
- Поддержка набора рабочих сценариев (очистка, остановка процессов, управление службами и т.д.).
- Криптографическая проверка подписи обновлений (сейчас только `sha256`, если передан).

## Конфигурация (переменные окружения)

- `GOSSS_AGENT_SERVER_URL` — базовый URL бэкенда (пример: `http://localhost:8080`)
- `GOSSS_AGENT_API_KEY` — ключ агента (`AGENT_API_KEY` на бэкенде)
- `GOSSS_AGENT_TYPE` — тип агента (по умолчанию `sssruner`)
- `GOSSS_AGENT_HEARTBEAT_SEC` — интервал heartbeat в секундах (по умолчанию `15`)
- `GOSSS_AGENT_UPDATE_CHECK_SEC` — интервал проверки обновлений (реализован через heartbeat) в секундах (по умолчанию `60`)
- `GOSSS_AGENT_DATA_DIR` — каталог данных агента (где хранится `agent.uuid`, временные файлы обновления)
- `GOSSS_AGENT_HOSTNAME` — принудительное имя хоста (опционально)

## Запуск в разработке

Пример для PowerShell:

```powershell
$env:GOSSS_AGENT_SERVER_URL="http://localhost:8080"
$env:GOSSS_AGENT_API_KEY="ваш-ключ-агента"
$env:GOSSS_AGENT_TYPE="sssruner"
go run .\cmd\etalon-agent
```

## Как работает heartbeat на текущем этапе

Агент отправляет минимальный payload:

- `hostname`
- `current_time`
- `agent_version`
- `uuid`
- `agent_type`

Сервер обновляет `last_heartbeat` и может вернуть список задач.

## Формат задачи самообновления (`self_update`)

Сервер может вернуть задачу в `tasks[]`:

```json
{
  "id": 123,
  "type": "self_update",
  "payload": {
    "version": "0.1.1",
    "download_url": "https://example.local/agent/goSSSagent.exe",
    "sha256": "hex_sha256_опционально",
    "file_name": "goSSSagent.exe",
    "args": []
  }
}
```

Что делает агент:

1. Скачивает файл.
2. Проверяет `sha256` (если передан).
3. Пытается заменить бинарник.
4. Перезапускает себя.

## Архитектурный задел под будущие задачи

Задачи должны выполняться как фиксированные сценарии (workflow), а не как произвольные скрипты.

Текущая структура уже подготовлена под это:

- `internal/runtime` — цикл агента, heartbeat, маршрутизация задач.
- `internal/workflows` — реализации сценариев (`self_update` и будущие сценарии).
- `internal/saga` — последовательное выполнение шагов с компенсацией.
