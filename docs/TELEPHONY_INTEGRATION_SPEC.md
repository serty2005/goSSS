# Спецификация для внешней LLM: план интеграции goSSS с внешней АТС

## 1. Назначение документа

Этот документ нужен как входной контекст для внешней большой языковой модели, которая должна подготовить поэтапный план внедрения интеграции с внешней автоматической телефонной системой.

Цель интеграции:

- принимать события звонков из АТС;
- автоматически связывать звонок с компанией, сотрудником, активом и/или уже существующим тикетом;
- автоматически создавать новые тикеты по звонкам там, где это оправдано;
- использовать расшифровки звонков, записи и метаданные вызова для обогащения карточки тикета;
- не ломать текущую архитектуру проекта и не дублировать уже существующие контуры синхронизации.

Документ фиксирует только то, что подтверждено текущим кодом и документацией. Там, где данных недостаточно, формулируются вопросы и требования к исследованию API АТС.

## 2. Фактический контекст текущего проекта

### 2.1. Архитектура backend

Проект построен на Go и использует смешанную архитектуру:

- HTTP API по схеме `handlers -> services -> repositories`;
- event-driven контур через `pkg/eventbus`;
- фоновые шлюзы и воркеры для внешних систем;
- PostgreSQL через GORM;
- Redis уже используется в Bitrix24-контуре.

Подтвержденные опорные точки:

- `internal/app/app.go`
- `internal/core/events/events.go`
- `internal/core/gateways/ticket_gateway.go`
- `docs/ARCHITECTURE.md`

### 2.2. Что уже есть в тикетной подсистеме

В системе уже существует полноценная локальная сущность тикета, а не только кэш из Naumen.

Подтверждено по `internal/domain/tickets/models.go`:

- тикет хранит `subject`, `description`, `result`, `status`, `priority`, `type`;
- тикет связан с `company_id`;
- тикет может быть привязан к активу через `asset_id` + `asset_type`;
- у тикета есть `assignee_id`, `reporter_id`;
- для внешних заявителей предусмотрены `reporter_name` и `reporter_email`;
- у тикета есть история, комментарии и вложения;
- у тикета есть поле `service_desk_uuid` для связи с внешним ServiceDesk;
- у тикета есть поля интеграции с Bitrix24.

Подтверждено по `internal/domain/tickets/history.go`:

- история хранит `action`, `field`, `source`, `old_value`, `new_value`, `meta`;
- сейчас есть источники `ui`, `bitrix`, `servicedesk`, `system`;
- отдельного источника `telephony` пока нет.

### 2.3. Доступные API-операции по тикетам

Подтверждено по `internal/transport/http/handlers/ticket_handler.go`:

- список тикетов;
- фильтры;
- карточка тикета;
- создание внутреннего тикета;
- привязка актива;
- вложения;
- комментарии;
- смена статуса;
- смена исполнителя;
- смена компании;
- обновление описания;
- обновление полей Bitrix24;
- удаление тикета;
- refresh комментариев из внешнего ServiceDesk;
- фиксация факта копирования данных подключений.

Текущий HTTP-контур уже умеет работать с:

- комментариями как отдельной сущностью;
- вложениями как отдельной сущностью;
- историей изменений;
- SSE-событиями `ticket.updated`.

### 2.4. Что уже есть по внешним системам

#### Naumen ServiceDesk

- не используется и не требует разработки.

#### Bitrix24

Подтверждено по `internal/app/bitrix_module.go`, `internal/services/bitrix_sync_service.go`, `internal/services/bitrix_incoming_service.go`:

- есть выделенный модуль интеграции;
- есть публичный webhook-роут;
- есть входящий и исходящий контуры;
- есть Redis Streams / suppress-логика / отдельные воркеры;
- комментарии и вложения уже используются как часть интеграционного сценария.

Вывод:

- Bitrix24-модуль является хорошим архитектурным образцом того, как в проекте оформляется новая внешняя интеграция.

### 2.5. Ограничения текущего создания тикета

Подтверждено по `internal/services/ticket_service.go`:

- `CreateInternal(...)` требует реального автора `authorID`;
- `CreateInternal(...)` требует заранее выбранного `assignee_id`;
- создание идет как внутренний пользовательский сценарий;
- для автоматической телефонии отдельного метода `CreateExternal` или `CreateFromCall` сейчас нет.

Вывод:

- для авто-создания тикета по звонку потребуется либо:
  - новый сервисный сценарий создания тикета из внешнего источника;
  - либо специальный технический пользователь + стратегия назначения исполнителя;
  - либо оба механизма одновременно.

## 3. Что внешняя модель должна считать целевым результатом

Нужен практический план внедрения нового контура интеграции телефонии в существующий backend goSSS.

План должен ответить:

- какие события АТС являются входными;
- каким способом их принимать: webhook, polling, комбинированный режим;
- как сохранять события и обеспечивать идемпотентность;
- как находить компанию, пользователя, актив и существующий тикет по звонку;
- в каких случаях создавать новый тикет, а в каких дополнять существующий;
- как использовать расшифровку и запись разговора;
- как встроить все это в текущие тикетные модели, историю, комментарии, вложения и event-driven контур;
- какие изменения нужны в БД, API, сервисах, UI и фоновых воркерах;
- как будет обеспечиваться безопасность, аудит, retries, дедупликация и наблюдаемость.

## 4. Основные возможные точки применения телефонии

### 4.1. Создание нового тикета по входящему звонку

Подход применим, если:

- звонок завершился разговором и расшифровка указывает на инцидент или сервисный запрос;
- звонок пропущен или оборван и требуется обязательный обратный контакт;
- по номеру не найден активный тикет, но найден клиент/компания;
- оператор АТС явно пометил звонок как обращение в поддержку;
- IVR/очередь указывает, что звонок относится к техподдержке.

### 4.2. Обогащение уже существующего тикета

Подход применим, если:

- найден активный тикет этого клиента;
- звонок явно ссылается на номер существующего тикета;
- звонок поступил от того же контакта/компании и в пределах короткого окна после создания тикета;
- сотрудник вручную связал звонок с тикетом;
- номер телефона или идентификатор очереди однозначно указывает на конкретную линию сопровождения.

### 4.3. Создание не полноценного тикета, а сигнала для оператора

Подход применим, если:

- данных от АТС недостаточно для уверенного создания тикета;
- есть только факт пропущенного вызова без расшифровки;
- невозможно определить компанию;
- текст расшифровки низкого качества;
- нужно сначала показать карточку звонка оператору и дать ему подтвердить действие.

В таком случае возможны два варианта:

- отдельная сущность `CallInbox` / `CallLead` / `CallReview`;
- либо технический черновик тикета со статусом, который явно выделяет необходимость ручной обработки.

### 4.4. Подсказки оператору без немедленного создания тикета

Подход применим, если:

- звонок уже идет;
- нужно показать оператору найденные открытые тикеты клиента;
- нужно показать инфраструктуру компании;
- нужно сразу вывести TeamViewer / AnyDesk / LiteManager / RDP данные;
- нужно дать оператору кнопку "создать тикет по звонку" с предзаполнением полей.

## 5. Возможные сценарии автоматического создания тикетов по звонкам

Внешняя модель должна оценить и разложить по приоритетам минимум следующие сценарии.

### 5.1. Пропущенный входящий звонок

Базовая логика:

- если звонок пропущен;
- если звонок пришел в очередь техподдержки;
- если номер определен;
- если по номеру найден клиент или ранее связанный контакт;

то система может:

- создать тикет типа "consultation" или "incident";
- либо создать тикет/задачу на обратный звонок;
- либо создать черновик на ручное подтверждение.

### 5.2. Разговор завершился и в расшифровке найден запрос на помощь (это уже поздний вариант, создавать сигнал нужно на этапе звонка. После звонка и получения расшифровки нужно уже находить тикет и обогащать его контекстом разговора)

Базовая логика:

- есть расшифровка или AI-summary;
- классификатор видит проблему, инцидент, сбой, запрос на подключение, запрос на настройку;
- по номеру или контексту найден клиент;

то система может:

- создать новый тикет;
- сгенерировать тему;
- подставить краткое описание;
- определить предполагаемый приоритет;
- выбрать тип тикета.

### 5.3. Повторный звонок по уже открытому инциденту

Базовая логика:

- найден активный тикет той же компании/контакта;
- звонок происходит в ограниченном временном окне;
- или в речи произнесен номер тикета; (этого не происходит почти никогда - 1 случай из 500)

то система должна:

- не плодить дубль;
- добавить в существующий тикет комментарий/историю;
- приложить расшифровку и ссылку на запись;
- при необходимости поднять приоритет или перевести статус.

### 5.4. Звонок после закрытия тикета

Базовая логика:

- найден недавний закрытый тикет;
- звонок связан с той же проблемой;

то система должна выбрать стратегию:

- переоткрытие существующего тикета;
- создание нового тикета с ссылкой на предыдущий;
- создание комментария в старом тикете и отдельного нового тикета для новой ветки.

Внешняя модель должна предложить вариант, который лучше соответствует текущему workflow статусов в проекте.

### 5.5. Голосовое меню или очередь уже содержит тему обращения

Если АТС передает:

- номер очереди;
- код IVR;
- выбранный пункт меню;
- тег кампании;
- skill group;

то эти данные можно использовать для:

- выбора типа тикета;
- выбора исполнителя или группы;
- выбора шаблона описания;
- маршрутизации в нужную поддержку.

## 6. Как использовать расшифрованные данные звонков для наполнения тикетов контекстом

### 6.1. Что можно извлекать из расшифровки

Минимальный набор полезных признаков:

- краткое summary звонка;
- формулировка проблемы;
- признаки срочности;
- упоминание конкретного оборудования;
- упоминание адреса, точки, филиала, кассы, сервера;
- упоминание номера существующего тикета;
- упоминание имени сотрудника или контактного лица;
- признаки повторного обращения;
- результат разговора: обещан выезд, нужен обратный звонок, проблема решена, требуется диагностика.

### 6.2. Куда именно укладывать этот контекст в текущей модели

Подтвержденные варианты в текущем проекте:

- `ticket.subject` для короткой темы;
- `ticket.description` для итогового структурированного описания проблемы;
- `ticket_comments` для полной расшифровки или AI-summary;
- `ticket_histories.meta` для машинно-обрабатываемых метаданных;
- `file_assets` + `ticket_file_links` для аудиозаписи, текстового файла расшифровки, JSON-артефактов;
- `asset_id` + `asset_type` для связи с найденным оборудованием;
- `reporter_name` для имени звонящего, если он не является локальным пользователем.

### 6.3. Какой формат контекста предпочтителен

Рекомендуемый практический формат для описания тикета:

- 1 строка: суть обращения;
- 1 блок: что не работает;
- 1 блок: кого затрагивает;
- 1 блок: что уже пробовали;
- 1 блок: извлеченные идентификаторы инфраструктуры;
- 1 блок: ссылка на запись звонка и технические метаданные вызова.

Рекомендуемый формат для комментария:

- полный или нормализованный summary расшифровки;
- отметка, что комментарий создан автоматически из звонка;
- ID звонка в АТС;
- длительность;
- направление;
- номер телефона;
- признак уверенности распознавания.

### 6.4. Что не следует писать напрямую в публичные поля без правил

Нужны отдельные правила для:

- персональных данных;
- платежных данных;
- кодов доступа;
- диктовок паролей;
- технических ключей;
- нецензурной или шумовой части расшифровки;
- фрагментов разговора, не относящихся к инциденту.

Внешняя модель должна предусмотреть:

- нормализацию;
- редактирование чувствительных данных;
- разделение публичного и внутреннего контекста;
- политику хранения записи и транскрипта.

## 7. Реальные точки интеграции в текущем backend

### 7.1. Новый публичный webhook-контур

Предпочтительный вариант по аналогии с Bitrix24:

- добавить новый публичный endpoint вида `/api/integrations/telephony/webhook`;
- вынести логику в отдельный handler;
- верифицировать подпись/токен от АТС;
- сохранять сырое событие до бизнес-обработки.

Почему это соответствует проекту:

- такой паттерн уже применяется для Bitrix24;
- проект уже разделяет публичные интеграционные роуты и защищенный внутренний API;
- для внешних событий уже есть event-driven каркас.

### 7.2. Новые события event bus

Рекомендуется не писать бизнес-логику прямо в handler.

Нужен отдельный набор событий, например:

- `telephony.call.received`
- `telephony.call.ringing`
- `telephony.call.answered`
- `telephony.call.completed`
- `telephony.call.missed`
- `telephony.call.recording.ready`
- `telephony.call.transcript.ready`
- `telephony.ticket.enrichment.requested`

Причина:

- проект уже использует событийную модель;
- это упростит retries, фоновые задачи и отложенную обработку тяжелых артефактов.

### 7.3. Промежуточное хранилище вызовов

Нужен отдельный персистентный контур, а не только прямое обновление тикета.

Минимально необходимы сущности:

- `telephony_calls`
- `telephony_call_events`
- `telephony_call_artifacts`
- при необходимости `telephony_call_ticket_links`

Минимальные поля вызова:

- внешний `call_id`;
- `provider`;
- направление;
- время начала/ответа/завершения;
- длительность;
- caller/callee;
- очередь/ivr/skill;
- оператор в АТС;
- URL записи или внешний `recording_id`;
- статус расшифровки;
- сырой payload;
- нормализованный summary;
- confidence;
- статус обработки;
- ссылка на найденный тикет;
- признак авто-создания тикета;
- причина принятого решения.

### 7.4. Новый сервис сопоставления звонка

Нужен отдельный доменный сервис, который определяет:

- локального пользователя по номеру телефона;
- компанию по звонящему номеру;
- активный тикет по компании и/или заявителю;
- актив по признакам из речи;
- исполнителя по очереди, IVR, компании, последнему активному тикету, дежурству.

Важно:

- в текущем домене телефоны явно есть только у `user` и в bitrix user cache;
- в доменной модели `company` телефонного поля нет;
- следовательно, внешняя модель должна предложить механизм хранения и сопоставления клиентских телефонов.

### 7.5. Новый сценарий создания тикета из внешнего источника

Текущий `CreateInternal` для телефонии неудобен, потому что он требует:

- `authorID`;
- `assignee_id`.

Поэтому внешняя модель должна спланировать один из вариантов:

- новый метод `CreateExternal(...)`;
- новый метод `CreateFromCall(...)`;
- использование технического пользователя и отдельной стратегии назначения;
- черновик без исполнителя, если бизнес это допустит.

План должен явно описать:

- какие поля обязательны;
- как выбирается `reporter_name`;
- как сохраняется телефон;
- что делать, если компания найдена, а исполнитель нет;
- можно ли создавать тикет без привязки к активу;
- как помечать источник создания.

### 7.6. История, комментарии и вложения

Телефония должна использовать уже существующие механизмы:

- комментарии для расшифровок и summary;
- вложения для аудио и текстовых артефактов;
- историю для машинных шагов и решений автоматики.

Рекомендуется добавить новый источник истории:

- `telephony`

И новые поля/типы метаданных в `TicketHistory.Meta`, например:

- `call_id`
- `provider`
- `direction`
- `caller`
- `callee`
- `queue`
- `transcript_confidence`
- `recording_file_id`
- `auto_action`

### 7.7. SSE / UI-контур

Текущая система уже использует SSE и событие `ticket.updated`.

Внешняя модель должна оценить, достаточно ли:

- публиковать стандартное `ticket.updated`;
- или нужен отдельный realtime-канал для звонков.

Минимально полезные UI-сценарии:

- всплывающая карточка звонка;
- подсказка по найденным открытым тикетам;
- быстрый переход к созданию тикета;
- кнопка "привязать к существующему";
- показ summary и записи звонка в карточке тикета.

## 8. Интеграция с текущей системой тикетов

### 8.1. С чем должен уметь работать новый контур

Новая телефония должна интегрироваться как минимум с:

- `Ticket`;
- `TicketComment`;
- `TicketHistory`;
- `Attachment` / `FileAsset` / `TicketFileLink`;
- `TicketFilter`;
- `TicketHandler`;
- `TicketService`;
- `ticket.updated` через event bus.

### 8.2. Где автоматизация даст наибольший эффект

Наиболее ценные точки:

- входящий звонок сразу создает контекст по клиенту и активным тикетам;
- завершенный разговор автоматически наполняет тикет summary;
- повторный звонок не создает дубль, а усиливает существующий тикет;
- пропущенный звонок автоматически попадает в обработку;
- запись разговора сохраняется как доказательная база;
- оператор получает готовый стартовый контекст, а не пишет описание вручную с нуля.

### 8.3. Какие текущие поля уже позволяют интеграцию без полной переделки

Можно сразу использовать:

- `reporter_name`;
- `company_id`;
- `asset_id`, `asset_type`;
- `description`;
- `comments`;
- `history.meta`;
- `attachments`;
- `service_desk_uuid` как индикатор связи с внешней системой;
- `sync_with_bitrix` и bitrix-поля, если звонок должен попадать и в Bitrix24.

### 8.4. Какие доработки почти наверняка понадобятся

Вероятные обязательные изменения:

- отдельный источник истории `telephony`;
- отдельный сервис создания тикета из звонка;
- хранение телефонных идентификаторов клиентов;
- таблицы вызовов и артефактов;
- идемпотентная обработка повторных webhook-ов;
- стратегия выбора исполнителя;
- стратегия поиска/слияния с существующим тикетом;
- правила публикации транскрипта в публичные и внутренние поля.

## 9. Предлагаемая логика принятия решения по звонку

Внешняя модель должна построить решение примерно вокруг такого пайплайна:

1. Принять событие из АТС.
2. Проверить подпись, схему и обязательные поля.
3. Проверить идемпотентность по `event_id` и/или `call_id`.
4. Сохранить raw payload.
5. Дождаться финального статуса звонка и артефактов.
6. Нормализовать номера телефонов.
7. Выполнить матчинг по пользователю, компании, активному тикету и активу.
8. Выполнить классификацию сценария:
   - новый тикет;
   - комментарий в существующий;
   - ручная обработка;
   - игнор.
9. Если появился transcript/summary:
   - обогатить тикет;
   - приложить артефакты;
   - записать историю;
   - опубликовать событие.
10. Зафиксировать решение и причины.

## 10. Обязательные требования к надежности

Внешняя модель должна включить в план:

- идемпотентность для webhook-ов АТС;
- retries с backoff;
- отложенную обработку, если transcript приходит позже завершения звонка;
- отделение приема события от тяжелой обработки;
- дедупликацию по `call_id`, `recording_id`, `transcript_id`;
- аудит всех автоматических решений;
- метрики и structured logs;
- контроль объема хранимых записей и транскриптов;
- безопасное скачивание аудио-файлов;
- ограничение доступа к чувствительным данным.

## 11. Что нужно отдельно исследовать по API АТС

Внешняя модель должна проверить по документации АТС и явно ответить на следующие вопросы.

### 11.1. Входные события

- Какие webhook-события доступны по звонку?
- Есть ли отдельные события для начала, ответа, завершения, пропуска, перевода, удержания?
- Приходит ли уникальный `call_id`?
- Приходит ли `event_id` для идемпотентности?
- Приходит ли информация о внутреннем операторе, очереди, группе, IVR?

### 11.2. Запись разговора

- Когда становится доступна запись?
- Приходит ли URL или нужен отдельный API-запрос?
- Нужна ли подпись/токен для скачивания?
- Можно ли хранить ссылку вместо бинарной копии?
- Какой TTL у ссылки?

### 11.3. Расшифровка

- Отдает ли АТС transcript сама или это отдельный модуль?
- Transcript приходит синхронно или отдельным событием?
- Есть ли speaker diarization?
- Есть ли confidence по фразам или сегментам?
- Есть ли готовый summary, intent, keywords?

### 11.4. Телефонная идентификация

- В каком формате приходят номера?
- Как различаются внешний абонент, внутренний оператор и переадресованные legs?
- Что считается одним звонком при переводе между операторами?
- Как отличить повторный дозвон по одному кейсу?

### 11.5. Безопасность

- Есть ли подпись webhook-а?
- Есть ли allowlist IP?
- Есть ли повторная доставка при ошибке?
- Какие SLA и лимиты по API?

## 12. Что нужно отдельно учесть по интеграции с Naumen и текущим ServiceDesk-контуром

Внешняя модель не должна предполагать уже готовую двустороннюю синхронизацию локально созданных тикетов с Naumen.

Подтверждено:

- чтение тикетов, комментариев и файлов из Naumen уже реализовано;
- обновление отдельных сущностей реализовано;
- создание тикета в Naumen через текущий `NaumenAdapter` не реализовано.

Поэтому в плане должны быть отдельно разведены два варианта:

### Вариант A. Телефония создает только локальный тикет goSSS

Подходит, если:

- телефония нужна прежде всего для рабочего места поддержки внутри goSSS;
- достаточно локальной карточки и опциональной синхронизации в Bitrix24;
- Naumen остается read-side для части тикетов.

### Вариант B. Телефония должна инициировать создание тикета еще и во внешнем ServiceDesk

Тогда внешний план обязан включить:

- реализацию `CreateTicket` для Naumen-адаптера;
- маппинг локальной модели тикета в API Naumen;
- стратегию сохранения `service_desk_uuid`;
- синхронизацию комментариев, файлов и статусов;
- правила, когда авто-созданный звонком локальный тикет должен создавать внешний тикет, а когда нет.

Для справки по Naumen REST API:

- общая документация: https://www.naumen.ru/docs/sd/Content/RESTful/REST_API_TOC.htm
- в коде проекта уже используются операции чтения и изменения через REST-клиент Naumen (`find`, `get`, `edit`, `create-m2m`, работа с комментариями и файлами).

## 15. Ключевые факты, которые внешняя модель должна считать обязательными

- В проекте уже есть локальная тикетная модель, история, комментарии и вложения.
- В проекте уже есть event-driven каркас и практика внешних webhook-интеграций.
- Для Bitrix24 уже реализован рабочий шаблон: webhook -> storage/queue -> service -> sync.
- Чтение тикетов из Naumen есть, создание тикета в Naumen через текущий адаптер отсутствует.
- Авто-создание тикета по звонку нельзя просто навесить на `CreateInternal`, не решив вопрос автора и исполнителя.
- Для хранения записи и транскрипта уже есть подходящая файловая модель внутри тикетной подсистемы.
- Для телефонии почти наверняка понадобится собственное персистентное хранилище вызовов и артефактов.
- Нужно явно спроектировать идемпотентность, дедупликацию и правила автоматического решения "новый тикет или обновление существующего".
