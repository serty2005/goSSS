# Архитектура Etalon-Server

Документ описывает потоки данных, фоновые процессы и правила принятия решений в системе.

## 1. Потоки данных (Data Flows)

### 1.1. Flow: Данные от Агента (Agent Data)
Этот поток отвечает за получение сырых данных с оборудования клиентов и обновление CMDB (Configuration Management Database).

1.  **Ingestion (Сбор):**
    *   **FTP:** `AgentFTPGateway` сканирует FTP-директорию. При обнаружении новых/измененных JSON-файлов, данные валидируются.
    *   **API:** `AgentHandler` принимает JSON через POST запрос.
2.  **Event Publishing:** При успешной валидации публикуется событие `agent.data.received` с пейлоадом `AgentDataPayload`.
3.  **Orchestration (Оркестрация):**
    *   `Orchestrator` слушает событие.
    *   Вызывает `ProcessingEngine.ProcessAgentData`.
4.  **Identification (Идентификация - Matcher):**
    *   `EntityMatcherService` ищет существующие сущности в БД по "Водопадному алгоритму":
        1.  **Сервер:** Поиск по `CRMID` или публичному `IP`.
        2.  **Рабочая станция:** Поиск по `TeamViewer ID` или `LiteManager ID` (комбинация).
        3.  **ФР:** Поиск по `SerialNumber`.
    *   Если найдено несколько сущностей по одному критерию -> Возвращается конфликт дубликатов.
5.  **Decision Making (Принятие решений):**
    *   `ProcessingEngine` сравнивает входящие данные с найденными сущностями.
    *   Формирует план действий (`ProcessingResult`):
        *   `ActionUpdate`: Если данные новые и доверенные (см. Business Rules).
        *   `ActionCreateTask`: Если обнаружен конфликт (смена владельца, дубликаты, новое оборудование).
6.  **Execution (Исполнение):** `Orchestrator` выполняет транзакцию (обновляет таблицы БД или создает задачу в `reconciliation_tasks`).

### 1.2. Flow: Синхронизация с Внешними Системами (Sync)
Этот поток отвечает за поддержание актуальности данных между локальной БД и ServiceDesk (Naumen).

1.  **Trigger:** Таймер в `SDeskGateway` (по умолчанию 10 мин).
2.  **Polling:** Гейтвей запрашивает краткие данные (Summaries) через `IntegrationManager` -> `InventoryProvider`.
3.  **Comparison:** Гейтвей сравнивает `LastModifiedDate` из внешней системы с локальной датой синхронизации.
4.  **Fetch & Publish:** Для измененных сущностей запрашивается полная модель и публикуется событие `servicedesk.entity.updated`.
5.  **Persist:** `Orchestrator` получает модель и сохраняет её в БД, обновляя связь `external_system_links`.

## 2. Реестр Воркеров (Workers Registry)

| Компонент | Ответственность | Триггер |
| :--- | :--- | :--- |
| **FRUpdateFounder** | Сравнивает данные ФР (прошивки, сроки ФН) в локальной БД с данными в ServiceDesk. При расхождении генерирует задачу `need_update`. | Таймер (раз в 6 часов) |
| **StatusActualityWorker** | Проверяет сущности со статусом `attention_required`. Если причина (например, дубликат) устранена, возвращает статус `ok`. | Таймер (раз в 2 мин) |
| **SDEditorWorker** | Асинхронно отправляет изменения в ServiceDesk (например, создание КЕ или обновление полей). Слушает события `servicedesk.entity.*.requested`. | EventBus |
| **ServerPollingGateway** | Опрашивает реальные сервера (iikoRMS/Syrve) по HTTP для проверки доступности и версии. Обновляет поле `status` (active/offline). | Таймер + EventBus (ручной запуск) |

## 3. Бизнес-правила (Business Rules)

### 3.1. Trusted Updates (Доверенное обновление)
Система не перезаписывает все поля подряд. Обновление происходит только по правилам:

*   **Server:**
    *   `CRM ID`: Обновляется из агента, только если в БД пусто.
    *   `Owner`: Не меняется автоматически (создается задача `owner_mismatch`), если уже задан.
*   **Workstation:**
    *   `TeamViewer`, `LiteManager`, `Hostname`: Обновляются всегда (источник правды — агент).
    *   `AnyDesk`: Игнорируется (временно, из-за нестабильности агента).
*   **FiscalRegister:**
    *   Full Trust: Все поля (`RNKKT`, `Firmware`, `Licenses`) обновляются из данных агента.

### 3.2. Конфликты
*   **Owner Mismatch:** Если агент присылает данные, но найденное оборудование привязано к другой компании.
    *   Проверка родства: Если компании связаны (холдинг/филиал) -> Игнорируем конфликт.
    *   Иначе -> Задача `owner_mismatch`.
*   **Duplicates:** Если найдены две сущности с одинаковыми идентификаторами (например, IP) -> Задача `resolve_duplicate`, обновление блокируется.
