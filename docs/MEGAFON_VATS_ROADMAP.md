# Roadmap интеграции goSSS с Мегафон ВАТС

## 1. Основание документа

Документ фиксирует текущий roadmap внедрения интеграции с Мегафон ВАТС на основе:

- утвержденных бизнес-границ;
- спецификации [TELEPHONY_INTEGRATION_SPEC.md](./TELEPHONY_INTEGRATION_SPEC.md);
- документации API Мегафон ВАТС из [rest_api.pdf](./rest_api.pdf);
- текущей архитектуры проекта goSSS.

Документ является рабочей базой для дальнейшего уточнения. Реальные payload-примеры, спорные статусы и точные правила будут добавлены позже без пересборки общей структуры решения.

## 2. Зафиксированный scope MVP

- Используем только внешние звонки.
- Внутренние звонки внутри компании не поддерживаются и в модель не включаются.
- Учитываем только тех сотрудников, которые:
- зарегистрированы в нашей системе;
- имеют включенную интеграцию с ВАТС;
- имеют сохраненный `login` сотрудника ВАТС.
- Мы не изменяем поведение самой ВАТС.
- Мы не управляем сотрудниками, отделами, маршрутами, DND, подписками, исходящими звонками и прочими настройками ВАТС.
- Мы только принимаем и читаем данные из ВАТС для:
- отображения текущего состояния линии;
- анализа звонков;
- привязки звонков и контактов к тикетам.
- Главный пользовательский сценарий MVP:
- сотрудник принимает внешний звонок;
- если активного тикета по этому номеру нет, система временно запоминает номер клиента и сотрудника;
- сотрудник создает тикет;
- система подставляет контакт и показывает связанный исторический контекст.

## 3. Методы и команды API Мегафон ВАТС, которые входят в MVP

### 3.1. Входящие команды от ВАТС в нашу систему

- `cmd=event`
- Назначение: realtime-состояние звонка.
- Источник: команда `event` из `rest_api.pdf`, стр. 7-8.
- Ключевые поля:
- `type=INCOMING|ACCEPTED|COMPLETED|CANCELLED|OUTGOING|TRANSFERRED`
- `callid`
- `phone`
- `user`
- `direction`
- `diversion`
- `groupRealName`
- `ext`
- `telnum`
- `telnum_name`
- `second_callid`

- `cmd=history`
- Назначение: финальный факт звонка, длительность, статус, запись, признак пропущенного и его итоговый статус.
- Источник: команда `history` из `rest_api.pdf`, стр. 6-7.
- Ключевые поля:
- `type`
- `user`
- `phone`
- `diversion`
- `start`
- `duration`
- `callid`
- `status`
- `link`
- `wait`
- `missedStatus`

### 3.2. Исходящие запросы из нашей системы в ВАТС

- `GET /crmapi/v1/users?with=status`
- Назначение: список сотрудников ВАТС и их текущие статусы регистрации.
- Источник: `rest_api.pdf`, стр. 19-20.
- Ключевые поля ответа:
- `login`
- `name`
- `position`
- `email`
- `ext`
- `telnum`
- `role`
- `mobile`
- `status`

- `GET /crmapi/v1/users/{login}`
- Назначение: точечная проверка конкретного сотрудника.
- Источник: `rest_api.pdf`, стр. 20-25.

- `GET /crmapi/v1/history/json`
- Назначение: backfill, сверка, восстановление пропущенных звонков, построение аналитики.
- Источник: `rest_api.pdf`, стр. 13-17.
- Нужные параметры:
- `uid`
- `start`
- `end`
- `period`
- `type`
- `limit`
- `user`
- `client`
- `groups`
- `first_answered`
- `processMissed`
- `missedStatus`

- `GET /crmapi/v1/domain`
- Назначение: диагностика домена и таймзоны.
- Источник: `rest_api.pdf`, стр. 52.

- `GET /crmapi/v1/record`
- Назначение: диагностика включенной записи звонков.
- Источник: `rest_api.pdf`, стр. 54-55.

## 4. Методы и команды API Мегафон ВАТС, которые исключены из MVP

- `cmd=contact`
- Исключается, потому что влияет на поведение ВАТС и может участвовать в маршрутизации звонков.
- `cmd=rating`
- Не нужен для первичного сценария тикетов.
- `POST /crmapi/v1/makecall`
- Исходящий звонок из интерфейса откладывается.
- `/crmapi/v1/history/inner/json`
- Внутренние звонки не нужны.
- Управление сотрудниками, отделами, DND, subscription, BLF, webhook-подписками.
- Раздел `Webhook` из `rest_api.pdf`, стр. 80-81, не используется для звонков в MVP.

## 5. Ключевые выводы из текущих данных

- Основной realtime-контур строится через входящие команды `event` и `history`, а не через отдельные webhook subscriptions ВАТС.
- Для живого индикатора линии в API нет готового отдельного метода "кто сейчас разговаривает", поэтому текущее состояние линии нужно собирать локально из `event`.
- Для состояния "сотрудник на линии" можно использовать `GET /users?with=status`.
- Для пропущенных и не перезвоненных звонков главным источником правды будет `history/json` с `processMissed=true` и полем `missedStatus`.
- Для записи звонка отдельный метод не нужен, так как ссылка приходит в `history.link` и `history/json.record`.
- В проверенной документации нет read-only каталога контактов ВАТС, поэтому имя контакта в MVP из ВАТС не получаем.

## 6. Архитектурное решение

Интеграция реализуется как отдельный модуль в приложении по образцу текущих интеграций Bitrix24 и Pyrus:

- отдельный `telephonyModule` в `internal/app`;
- отдельный handler публичного webhook endpoint;
- отдельный service inbound-обработки;
- отдельный sync service для чтения сотрудников и истории;
- отдельный repository и доменные модели телефонии;
- отдельные события для event bus и SSE;
- отдельный UI-контур для линии, popup и аналитики.

При этом тикетный контур не переписывается с нуля. Мы расширяем его через:

- новую сущность контакта;
- новую связь контакта с тикетом;
- pending-context для ручного создания тикета после принятого звонка;
- отдельные telephony-endpoints для UI.

### Фаза 3. Прием и обработка входящих событий звонков

Цель: построить надежный inbound pipeline.

Поддерживаемые команды:

- `event`
- `history`

Pipeline:

1. принять webhook;
2. проверить `crm_token`;
3. вычислить `payload_hash`;
4. сохранить `telephony_incoming_event`;
5. проверить идемпотентность;
6. поставить событие в очередь обработки;
7. обработать в воркере;
8. выполнить upsert в `telephony_calls`;
9. сохранить детальный шаг в `telephony_call_events`.

Правила обработки:

- `event` обновляет текущее состояние звонка;
- `history` финализирует звонок;
- если `history` пришел без всей цепочки `event`, звонок все равно должен быть собран;
- `TRANSFERRED` связывается по `callid` и `second_callid`;
- `recording_url` обновляется из `history`, если там появилась запись;
- только внешние звонки попадают в `telephony_calls`, внутренние игнорируются.

Результат:

- данные о звонках устойчиво накапливаются;
- дубликаты не плодятся;
- переводы и завершения звонков не теряются.

### Фаза 5. Контакты и связь с тикетами

Цель: встроить телефонию в тикетный домен без автосоздания тикетов.

Задачи:

- добавить локальную сущность контакта;
- при каждом внешнем звонке:
- нормализовать телефон;
- найти или создать `contact`;
- обновить связь контакта с компанией, если компания уже известна;
- позже поддержать nullable-привязку к Bitrix24 контакту;
- добавить в тикет новое поле "Контакт";
- сохранить связь тикета с контактом через `contact_id`.

Ограничение:

- имя контакта из самой ВАТС не получаем, так как в доступной документации нет read-only метода каталога контактов.

Результат:

- контакт становится отдельной сущностью;
- тикет получает штатную связь с контактом;
- появляется база для будущей интеграции с Bitrix24 контактами.

### Фаза 6. Flow "принял звонок -> создал тикет"

Цель: реализовать главный пользовательский сценарий MVP.

Логика:

- если поступил новый звонок;
- если активного тикета по номеру не найдено;
- если известен сотрудник, который принял звонок;
- создается `telephony_pending_context`.

Дальше:

- сотрудник открывает `NewTicketModal`;
- система находит его pending-context;
- автоматически подставляет телефон контакта;
- слева сначала показывает компании, с которыми этот номер уже был связан;
- после выбора компании слева остается текущая логика последних тикетов компании.

Новые backend endpoint-ы:

- `GET /api/telephony/pending-context/me`
- `POST /api/telephony/pending-context/{id}/bind-ticket`
- `GET /api/telephony/contacts/{contactId}/companies`
- `GET /api/telephony/users/{id}/calls`

Изменения frontend:

- расширить `NewTicketModal`;
- добавить поле контакта;
- добавить prefill из pending-context;
- добавить список компаний по номеру;
- после выбора компании использовать текущий сценарий последних тикетов компании.

Результат:

- сотрудник не вводит номер вручную;
- тикет создается в связке с реальным звонком и контактом;
- пользователь получает полезный исторический контекст.

### Фаза 7. Realtime-линия и header

Цель: показать состояние линии в header страницы тикетов.

Backend:

- `GET /api/telephony/line`
- SSE-событие `telephony.line.updated`

Frontend:

- использовать `headerAddon` в layout header;
- добавить круглый индикатор с подписью:
- `На линии: n сотрудников`
- при клике раскрывать popup по аналогии с существующими header controls.

Правила цвета:

- `blue`
- есть пропущенный и не закрытый обратным действием звонок клиента;
- `yellow`
- есть активный разговор сотрудника с клиентом;
- `green`
- есть хотя бы один интегрированный сотрудник `online`, но активного разговора нет;
- `red`
- интегрированных сотрудников на линии нет.

Содержимое popup:

- список текущих сотрудников линии;
- состояние каждого:
- `online`
- `in_call`
- ниже счетчик пропущенных, если они есть;
- клик по сотруднику ведет на страницу его звонков.

Результат:

- в шапке тикетов появляется живой статус линии;
- оператор сразу видит, кто на линии, кто в разговоре и есть ли необработанные пропущенные звонки.

4. админская таблица;
5. realtime-линия в header;
6. pending-context и prefill в тикетах;
7. включение для пользователей.

Результат:

- внедрение идет контролируемо;
- каждая стадия может быть проверена отдельно.

## 8. Что явно отложено

- автосоздание тикета;
- команда `contact`;
- команда `rating`;
- исходящий звонок через `makecall`;
- управление ВАТС через API;
- внутренние звонки;
- транскрипты и AI-summary, если Мегафон не предоставляет отдельный канал;
- двусторонняя синхронизация контактов с Bitrix24.

## 9. Открытые вопросы, которые будут уточнены позже

- реальные примеры payload для `event` и `history`;
- точный перечень фактических статусов сотрудника в `/users?with=status`;
- окончательная трактовка `missedStatus`;
- TTL и стабильность `record` URL;
- нужно ли локально копировать запись разговора или достаточно хранить ссылку;
- точный TTL для `telephony_pending_context`;
- правила выбора компании, если номер был связан с несколькими компаниями;
- финальные RBAC-ограничения для просмотра чужих звонков и записей.

## 10. Итог

Текущее решение для MVP строится вокруг read-only интеграции с Мегафон ВАТС:

- читаем сотрудников;
- принимаем события звонков;
- сверяем историю звонков;
- строим собственное состояние линии;
- связываем звонки, контакты и тикеты внутри goSSS;
- не вмешиваемся в маршрутизацию и настройки самой ВАТС.

Этого достаточно, чтобы закрыть:

- индикатор линии;
- просмотр звонков сотрудников;
- админскую таблицу звонков;
- привязку номера клиента и исторического контекста к созданию нового тикета.
