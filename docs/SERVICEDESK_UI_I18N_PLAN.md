# ServiceDesk UI: план мультиязычности и редактора переводов

## Назначение документа

Этот документ нужен как единая опорная точка для всех последующих сессий по внедрению мультиязычности в UI ServiceDesk.

Цели:

- перевести интерфейс с текущего русского на английский;
- заложить архитектуру для добавления новых языков без переделки UI;
- централизовать все пользовательские тексты, даты, статусы, уведомления и подписи;
- подготовить основу для будущего редактора переводов прямо из UI;
- вести работу итеративно, но без архитектурного долга.

## Текущее состояние UI

По результатам первичного аудита:

- UI расположен в `front-ui/`;
- стек: React 19, TypeScript, Vite, Ant Design, Zustand, TanStack Query, dayjs;
- сейчас локализация отсутствует как системный слой;
- значительная часть текстов зашита прямо в компонентах и страницах;
- `ConfigProvider` Ant Design уже использует жёстко заданную русскую локаль;
- форматирование дат выполняется смешанно: через `dayjs(...).format(...)` и `new Date(...).toLocaleString()`;
- тесты местами завязаны на русские тексты;
- часть ошибок приходит как свободный текст от backend, что создаёт риск для английского UI.

Ключевые проблемные зоны:

- layout и навигация;
- фильтры, таблицы, формы, placeholders;
- статусы и enum-метаданные;
- уведомления `message.*`, `Modal.*`, `Popconfirm`;
- форматирование даты/времени;
- тесты, завязанные на текст;
- отображение backend-ошибок;
- отсутствие единого хранилища и стратегии загрузки переводов.

## Целевое архитектурное решение

### Библиотеки

Базовый стек локализации:

- `i18next`
- `react-i18next`

Дополнительно:

- locale-модуль Ant Design через `ConfigProvider`;
- locale-модуль `dayjs`.

### Общие принципы

1. Все пользовательские тексты идут через `t(...)`.
2. Используются семантические ключи, а не текстовые ключи.
3. Переводы разбиваются на namespaces.
4. Базовые локали хранятся в репозитории.
5. Архитектура допускает наложение удалённых переводов поверх локальных.
6. Выбранный язык хранится у пользователя в `profile_config.interface.locale`.
7. Есть единый locale registry, который знает:
   - код языка;
   - отображаемое название;
   - locale для Ant Design;
   - locale для dayjs;
   - статус доступности;
   - язык по умолчанию.


### Предлагаемые namespaces

- `common` — общие кнопки, действия, лейблы, состояния загрузки, пустые состояния;
- `layout` — меню, header, профиль, тема, уведомления shell;
- `auth` — логин, пароли, авторизация;
- `dashboard` — overview и карточки статистики;
- `tickets` — списки, детали, редактор, история, комментарии, формы;
- `companies`
- `equipment`
- `agents`
- `admin`
- `profile`
- `reports`
- `validation` — типовые сообщения формы;
- `errors` — локализованные fallback-ошибки и маппинги ошибок.

### Формат ключей

Примеры:

- `common.actions.save`
- `common.actions.cancel`
- `common.states.loading`
- `layout.menu.tickets`
- `layout.theme.day`
- `auth.login.submit`
- `tickets.list.columns.number`
- `tickets.details.comments.private`
- `tickets.status.new`
- `validation.required.company`
- `errors.network.default`
- `errors.auth.invalidCredentials`

Не использовать:

- ключи вида `"Войти"`;
- случайные короткие ключи без домена;
- дублирующиеся ключи для одинакового смысла.

## Хранение выбранного языка

### Целевое место хранения

В `profile_config.interface.locale`.

Предлагаемое расширение DTO:

```ts
interface UserInterfaceConfigDTO {
  theme_mode?: 'light' | 'dark';
  locale?: 'en' | 'ru' | string;
  theme_palettes?: {
    light?: ThemePaletteConfigDTO;
    dark?: ThemePaletteConfigDTO;
  };
  search?: {
    cards_columns?: number;
  };
}
```

### Правила выбора языка при старте

Порядок:

1. `user.profile_config.interface.locale`, если пользователь авторизован и значение валидно;
2. локально сохранённая locale в браузере, если это допустимо архитектурой;
3. `en` как целевой дефолт;
4. fallback на `ru`, если по каким-то причинам `en` не загружен.

### Переключение языка

Переключение должно:

- менять язык в `i18next`;
- менять locale в Ant Design;
- менять locale в `dayjs`;
- по возможности сохранять выбор в `profile_config`;
- не требовать перезагрузки страницы.

## Работа с Ant Design и dayjs

### Ant Design

Нужно убрать жёсткую привязку к одной locale и перейти на выбор locale по текущему языку.

Нужен маппинг примерно такого вида:

```ts
{
  en: enUS,
  ru: ruRU,
}
```

### dayjs

Нужно:

- загрузить locale для используемых языков;
- переключать глобальную locale через `dayjs.locale(...)`;
- постепенно вынести форматирование дат в единый слой.

### Единый слой форматтеров

Нужен набор helper-функций, например:

- `formatDate(value, locale)`
- `formatDateTime(value, locale)`
- `formatRelativeTime(value, locale)`
- `formatDateForTicketStamp(value, locale)`
- `formatLocaleDateTime(value, locale)`

Нельзя оставлять хаотичные вызовы:

- `new Date(...).toLocaleString()`
- `dayjs(...).format('DD.MM.YYYY HH:mm')`

в пользовательских компонентах без общего контекста локали.

## Стратегия миграции строк

### Что обязательно переводить

- заголовки страниц;
- подписи полей;
- placeholders;
- кнопки;
- меню;
- теги и статусы;
- empty states;
- уведомления `message.*`;
- `Modal`, `Popconfirm`, `Tooltip`;
- служебные подписи, aria-label, title, helper text;
- строки в карточках, таблицах и деталях;
- fallback-значения вроде `Не назначен`, `Неизвестно`, `Нет описания`.

### Что требует отдельного внимания

- строки, пришедшие с backend;
- названия интеграций и внешних систем;
- значения enum-типов;
- human-readable описание history entries;
- тестовые сценарии, где текст используется как селектор.

### Что не переводится автоматически

- пользовательские данные;
- данные от внешних систем без маппинга;
- свободный текст из тикетов, комментариев и описаний;
- server-side сообщения, если у них нет кода или карты локализации.

## Backend-ошибки и fallback-стратегия

Сейчас часть экранов показывает серверный текст как есть. Для мультиязычности это недостаточно.

Целевой подход:

1. Если backend начнёт отдавать стабильный `error_code`, использовать маппинг `error_code -> i18n key`.
2. Если приходит только текст, показывать:
   - локализованный общий fallback;
   - сырой серверный текст только как дополнительную техническую деталь, если это уместно и безопасно.
3. Для известных кейсов ввести frontend-мэппинг:
   - `invalid_credentials`
   - `network_error`
   - `timeout`
   - `unknown_error`

Пример целевого паттерна:

```ts
message.error(resolveApiErrorMessage(error, t));
```

## Тестовая стратегия

### Базовые правила

1. Тесты не должны массово зависеть от русских строк.
2. Для функциональных действий лучше использовать:
   - роли;
   - `aria-label`;
   - `data-testid`;
   - фиксированную locale тестовой среды.
3. Для snapshot-подобных и текстовых сценариев язык должен быть явно зафиксирован.

### Целевой подход

- в тестовой среде принудительно использовать `en`;
- там, где текст не является сутью сценария, заменить селекторы на устойчивые;
- для компонентов с критически важной локализацией добавить unit/smoke-тесты на переключение языка.

### Что проверить тестами

- смена языка обновляет UI без перезагрузки;
- Ant Design контролы меняют locale;
- даты форматируются в соответствии с выбранным языком;
- сохранение языка в профиле работает корректно;
- missing key не ломает UI;
- fallback `en -> ru` или `ru -> en` работает по выбранной стратегии.

### Этап 10. Редактор переводов в UI

Цель:

- дать возможность управлять переводами из интерфейса.

Это конечный этап, запускать его только после стабилизации базовой мультиязычности.

#### Функциональная цель редактора

Редактор должен позволять:

- выбирать язык;
- выбирать namespace;
- видеть список ключей и текущие значения;
- искать по ключу и по тексту;
- видеть, где перевод отсутствует;
- редактировать переводы;
- сохранять переводы;
- просматривать diff относительно базового перевода;
- фильтровать только missing/changed keys;
- при необходимости публиковать изменения.

#### Минимальная целевая модель данных

Базовая запись перевода:

```ts
type TranslationEntry = {
  locale: string;
  namespace: string;
  key: string;
  value: string;
  base_value?: string;
  status?: 'base' | 'override' | 'missing' | 'changed';
  updated_at?: string;
  updated_by?: string;
};
```

#### Предпочтительная архитектура

Источники:

1. base translations из репозитория;
2. override translations из backend;
3. результирующий merged view в UI.

#### Рекомендуемый backend-контур для будущего
