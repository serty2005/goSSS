# Интеграция ServiceDesk с Pyrus

## Назначение

Эта интеграция нужна для синхронизации обращений из единого центра поддержки iiko в Pyrus с локальным ServiceDesk партнёра и обратно.

Базовый принцип:

- первое сообщение всегда приходит из Pyrus;
- если `ext_id` пустой, создаётся новый локальный тикет;
- если `ext_id` заполнен, сообщение из Pyrus добавляется в уже существующий локальный тикет;
- ответы оператора из ServiceDesk должны уходить обратно в Pyrus;
- закрытие тикета в ServiceDesk должно закрывать задачу в Pyrus и в Помощнике.

## Источник требований

Спецификация составлена по документу [pyrus_docs.docx](/c:/safe/repos/goSSS/docs/pyrus_docs.docx).

## Обязательные параметры интеграции

- Форма Pyrus единого центра поддержки iiko: `2315062`.
- Поле связи с локальным тикетом: `ext_id`.
- Авторизация в Pyrus API: `POST /v4/auth`.
- Отправка комментария в Pyrus: `POST /v4/tasks/{task_id}/comments`.
- Загрузка вложений в Pyrus: `POST /files/upload`.
- Скачивание вложений из Pyrus: `GET /files/download/{file-id}`.

## Поля, которые нужно читать из Pyrus

Из задачи формы `2315062` ServiceDesk обязан использовать следующие текстовые поля:

- `CRMID`
- `Restaurant`
- `Module`
- `CallType`
- `Subject`
- `SenderName`
- `ext_id`

## Входящий флоу: Pyrus -> ServiceDesk

### 1. Приём webhook

ServiceDesk принимает `POST /api/integrations/pyrus/webhook`.

Требования:

- `Content-Type` должен начинаться с `application/json`;
- подпись webhook проверяется по `X-Pyrus-Sig`;
- payload сохраняется как входящее событие с дедупликацией по hash тела;
- обработка выполняется асинхронно через worker.

### 2. Определение типа события

После разбора webhook извлекается `task_id` и задача Pyrus.

Важные проверки:

- задача должна относиться к форме `2315062`;
- если задача подавлена anti-loop ключом, событие игнорируется;
- если webhook не содержит полной задачи, задача догружается через Pyrus API.

### 3. Если `ext_id` пустой

Это новое обращение.

Нужно:

- определить локальную компанию по `CRMID`;
- создать новый тикет в ServiceDesk;
- записать связь `ticket_id <-> pyrus_task_id`;
- импортировать вложения из задачи и комментариев;
- импортировать комментарии клиента;
- опубликовать обратную синхронизацию `ext_id` в Pyrus.

### 4. Если `ext_id` заполнен

Это существующее обращение.

Нужно:

- найти локальный тикет по `ext_id`;
- обновить связь `ticket_id <-> pyrus_task_id`;
- импортировать новые вложения;
- импортировать новые комментарии клиента;
- синхронизировать статус локального тикета из Pyrus, если он изменился.

## Исходящий флоу: ServiceDesk -> Pyrus

### 1. Обратная запись `ext_id`

После создания локального тикета из Pyrus ServiceDesk должен вызвать:

- `POST /v4/tasks/{task_id}/comments`

В запросе нужно:

- передать служебный комментарий;
- передать `field_updates` для поля `ext_id`;
- записать в `ext_id` идентификатор локального тикета.

### 2. Ответ оператора

Когда оператор добавляет публичный комментарий в локальный тикет, ServiceDesk должен вызвать:

- `POST /v4/tasks/{task_id}/comments`

В запросе обязательно:

- передавать текст комментария;
- передавать `channel.type = mobile_app`;
- предварительно загружать все вложения комментария через `POST /files/upload`;
- передавать GUID загруженных файлов в `attachments`.

Приватные комментарии в Pyrus не отправляются.

### 3. Закрытие тикета

Если локальный тикет переведён в `resolved` или `closed`, ServiceDesk должен вызвать:

- `POST /v4/tasks/{task_id}/comments`

В запросе обязательно:

- указывать `action = finished`.

Если задача в Pyrus уже закрыта, а локальный статус переводится обратно в рабочий, перед закрытием/сменой статуса допускается использовать `action = reopened`.

## Работа с вложениями

### Входящие вложения из Pyrus

- скачиваются через `GET /files/download/{file-id}`;
- сохраняются во внутреннее файловое хранилище;
- связываются с тикетом и/или комментарием;
- дедуплицируются по `pyrus_attachment_id`.

### Исходящие вложения в Pyrus

- читаются из локального файлового хранилища;
- для каждого файла вызывается `POST /files/upload`;
- возвращённый `guid` передаётся в `attachments` комментария.

## Правила синхронизации комментариев

- служебный комментарий, который только обновляет `ext_id`, не должен импортироваться в локальный тикет как обычное сообщение;
- уже импортированные комментарии повторно не создаются;
- исходящий комментарий из ServiceDesk должен иметь link с `pyrus_comment_id`, если Pyrus вернул созданный комментарий;
- при смене статуса перед закрытием нужно сначала догрузить все публичные комментарии оператора, которые ещё не были отправлены в Pyrus.

## Наблюдаемость и логи

Для Pyrus-интеграции должны быть видны следующие этапы:

- webhook принят;
- payload разобран;
- событие сохранено в БД;
- событие поставлено в очередь;
- worker поднял событие в обработку;
- задача загружена из webhook или через API;
- выбрана ветка `new ticket` или `existing ext_id`;
- созданы/обновлены тикет, комментарии, вложения;
- опубликована обратная запись `ext_id`;
- отправлены комментарии, статусы и вложения в Pyrus;
- событие завершено, проигнорировано или упало с ошибкой.

## Конфигурация

Минимально необходимые переменные:

- `ENABLE_PYRUS_GATEWAY=true`
- `PYRUS_WEBHOOK_ENABLED=true`
- `PYRUS_LOGIN`
- `PYRUS_SECURITY_KEY`
- `PYRUS_WEBHOOK_SECRET`
- `PYRUS_FORM_ID=2315062`
- `TICKET_STORAGE_PATH`

Если `PYRUS_FORM_ID` не задан, по умолчанию используется `2315062`.

## Проверочный чек-лист

1. Новый тикет создаётся из webhook с пустым `ext_id`.
2. После создания локального тикета `ext_id` записывается обратно в Pyrus.
3. Повторный webhook по той же задаче с заполненным `ext_id` добавляет комментарий в локальный тикет.
4. Публичный комментарий оператора уходит в Pyrus с `channel.type = mobile_app`.
5. Вложения оператора загружаются в Pyrus и прикрепляются к комментарию.
6. Перевод тикета в `resolved` или `closed` закрывает задачу через `action = finished`.
7. В логах видна вся цепочка прохождения события без silent-failure.
